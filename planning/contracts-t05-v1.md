# T05 provider and evaluation handoff

## T06 adapter interface

`readProviderConfig()` reads server environment only. Explicit `COACH_PROVIDER=openai` requires `OPENAI_API_KEY` and `OPENAI_MODEL`; no model or account availability is assumed. `fixtures` is allowed only under `NODE_ENV=test|development`; production/unset environments reject it. T06 implements fixture responses; the T05 live adapter refuses fixture configuration. Invalid configuration throws fixed `ConfigurationError/CONFIGURATION_ERROR`, without raw values.

Create one `createProviderSession(request, {config, signal?, transport?})` per valid request. It validates/clones the request and exposes ordered `classify()`, `generate('plan'|'clarify')`, `review(candidate)` operations. They return `ProviderResult<Classification|CoachResponse|Review>` respectively. At most three calls, no repeated/concurrent stages, no retry after failure. The shared 20-second deadline starts at creation, including idle time between stages. Calls use strict object-rooted wire schemas, separate untrusted JSON input, `store:false`, no tools/streaming, 1,200 output tokens maximum, and zero SDK/per-call retries. Cancellation aborts upstream and discards late results even with an injected transport ignoring the signal. Timers/listeners are removed on completion.

Results contain validated `value`, nullable token `usage`, stage duration, `operation`, `requestedModel` and nullable provider-reported `returnedModel`. An alias does not establish a resolved snapshot. `ProviderError` contains a fixed code, nullable known usage and sanitized operation/model/duration metadata. No SDK/Zod body, cause, headers or input content escapes. Codes: `INVALID_INPUT`, `CALL_BUDGET`, `CANCELLED`, `TIMEOUT`, `REFUSAL`, `INCOMPLETE`, `EMPTY_OUTPUT`, `INVALID_OUTPUT`, `UPSTREAM`. T06 maps these to existing public envelopes or known-risk authored fallbacks; these are not new public contract codes.

Generation validates requested family/locale and complete application bounds. Review validates the candidate and decision/category relationship. This adapter does not establish semantic safety or approve coaching. T06 must apply T04's `beforeClassification`, `afterClassification`, `afterReview`, skip provider work for explicit emergency, preserve known-risk fallbacks and validate final correlation. Review must receive the exact candidate considered for release. Classification failure/unknown must never become routine.

Tests inject a transport; separate fake-fetch regressions exercise the actual pinned SDK without network. Only the guarded provider module imports the SDK. Its fixed API endpoint and disabled SDK logs prevent environment overrides from redirecting messages or emitting content. `store:false` is not zero retention; see [official data controls](https://developers.openai.com/api/docs/guides/your-data). Schemas follow [official Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs); live schema/model acceptance remains unverified.

## Evaluation and T09 seam

`npm run eval:live` is **dry-run by default**, despite its test-strategy script name. It validates 35 seed + 6 AI-authored held-out cases and estimates three calls per supplied turn. Possible-escalation cases repeat at least three times. One candidate produces 83 planned attempts/273 maximum calls; two produce 166/546. These are budgets, not measured calls, costs or quality.

`--models candidate-a,candidate-b` accepts explicit account-available candidates; availability is not inferred. Live requires `--live`, an explicit model list, key and sufficient integer `--max-calls` (ceiling 5,000). Options, duplicates and transcript bounds are checked before network work. No live inference runs in CI. An approved spend envelope is still required before paid evaluation.

The current CLI runs **direct-provider diagnostics**, not T06 policy or endpoint evaluation. JSONL records include expected families/categories, requirements, classification/candidate/review observations, requested/returned models, all revisions, per-stage tokens/latency, sanitized failures and nullable human scores/reviewer. Candidate observations are not accepted coaching: `actualKind/actualCategory` remain null without a pipeline response. Billed failed stages preserve known usage/metadata; absent usage is unknown. Outputs use exclusive creation and owner-only permissions under ignored `evaluation-results/` by default; existing results cannot be overwritten.

The exported `EvaluationTarget`/`evaluateCase` seam accepts a later integrated pipeline and validates both setup and final responses, including locale. It sends ordered setup parent turns and retains only real accepted replies. Errors, missing responses and invalid replies stop the case; no history is fabricated. Diagnostics cannot supply accepted setup: EN03, HI01, HI02 and HO06 stop with `SETUP_NOT_ACCEPTED` before their latest concern. These are not successful evaluations. T09 must inject T06, preserve the three-call/turn bound and run all cases/repetitions with human scoring. Diagnostic runs cannot select a production model or satisfy release gates.

Held-out Urdu/Roman Urdu paraphrases are AI-authored, pending native review, and not prompt examples. Native-authored cases/signoff, safeguarding review, full-pipeline live evaluation and final model selection remain T09 gates.
